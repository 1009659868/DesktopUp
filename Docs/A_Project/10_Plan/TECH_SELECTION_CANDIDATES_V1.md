## 3. 参考项目调研

### 3.1 壁纸引擎类（产品形态参考）

- **Wallpaper Engine**：C++ 核心；web 壁纸用 **CEF 离屏渲染**后作为纹理合成进自有场景渲染器；场景壁纸是自有引擎。验证了"引擎核心 + 离屏 web 渲染 + 自有合成"是壁纸引擎的标准形态，也说明**主题自由度由引擎决定，不由浏览器窗口决定**。
- **Lively Wallpaper**（开源，C#）：核心/UI 与壁纸播放**进程隔离**（每种壁纸类型独立 player 进程：mpv / WebView2 / 视频），主程序只做调度、墙纸定位与输入转发。进程隔离模型与本画像"渲染崩溃有限重建、不拖死核心"直接对应。
- **Rainmeter**：C++，皮肤 = INI + 数据驱动度量 + 可选 Lua，无任意代码也形成庞大皮肤生态——证明**数据驱动主题可以达到很高自由度**，受限代码不是唯一路线。

### 3.2 桌面层与透明窗口类（V1 教训对照）

- **zebar**（glzr-io，wry 透明窗口桌面条）：社区记录过透明 widget 条带伪影（issue #252 等）——与 V1 白条同族，佐证"透明浏览器窗口直接上桌面层"在同类产品同样不可靠。
- **TranslucentTB**：任务栏透明使用 `SetWindowCompositionAttribute` 现代路径——只是参考其窗口合成属性用法，不是我们的宿主方案。
- **Seelen UI**（Rust/Tauri 的 Win11 桌面定制）：同类产品正在做的方向；但其 UI 主体仍是浏览器系窗口，桌面层长期稳定性同样受 V1 类问题约束，仅作为生态现状参考。

### 3.3 渲染解耦类（技术形态参考）

- **OBS browser source**（obs-browser）：CEF 离屏 → 共享纹理 → OBS 合成器。证明"浏览器渲染 + 应用自有合成"可以完全避开浏览器窗口/透明窗口问题，代价是 CEF 载荷（约 100MB+）与复杂度。
- **WebView2 Composition Controller**（官方 API）：允许应用把 WebView2 内容放进自己的 DirectComposition 视觉树。它是"保留 HTML/CSS 主题 + 应用自有合成"的轻量路线；已知问题：变换/重绘相关 bug（WebView2Feedback #5400 等），且"自定义视觉树 + Win11 每像素透明"正是 V1 未能验证的地带——必须原型验证，不能假设成立。

## 6. 原型建议与验证矩阵

按"可靠性风险最高者先证伪、自由度与预算按用户权重"给出两组路线，任选其一或并行：

### 路线甲（推荐）：Qt 6 Quick/QML 优先，原生 D2D 保底

1. **原型 D**：透明圆角海报 + 自制标题栏 + 六占位卡片 + QML 参数主题（不接控制中心/SQLite/托盘）；
   - 必须证明：20 轮拖动零白条/灰框/裁切；空白穿透 + 命中区域；Win+D/Explorer 重启；静态 0 FPS（无绘制循环）；内存实测；QML 受限组件白名单的可行性骨架。
2. 原型 D 通过 → 选定 Qt；失败 → 原型 E（原生 D2D，主题自由度折中但可靠性/预算最佳）。
3. 若用户强烈偏好 HTML/CSS 主题 → 原型 B（Composition Controller）作为并行第二候选，与 D 跑同一矩阵。

### 路线乙：Web 主题优先

1. 原型 B（Composition Controller）先行；失败 → C（CEF 离屏，接受载荷与内存预算上调）或 D。

### 每个原型的固定证据矩阵（来自画像）

1. 冷启动、拖动 20 轮、CC 开关 10 轮、收起/展开 10 轮：零顶部条带/灰框/裁切；
2. 空白框选/右键/原生图标穿透；标题栏与 Item 命中精确；
3. 海报不覆盖普通程序与文件选择器；Win+D、Explorer 重启恢复；
4. 静态 0 FPS 实测（无持续绘制）；10s CPU ≤0.10s；工作集实测并记录（超出 50MiB 需用户接受）；
5. 呈现自检能力验证（可检测 S1/S2/S3 类劣化）；
6. 安装器携带运行时依赖的净机安装路径（或 WebView2 Evergreen 零载荷确认）；
7. 主题 L0–L3 等价能力骨架（schema 参数、素材槽、受限覆盖、热切换 <200ms）；
8. 渲染崩溃隔离与有限重建（进程边界或同进程兜底）。
