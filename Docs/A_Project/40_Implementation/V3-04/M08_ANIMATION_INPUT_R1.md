## 1. 用户反馈与证据

用户确认此前提供的三个步骤通过：A离开延迟收起/进入标题展开；期限内重入取消并在再次离开后重计；手动收起后须真正离开再进入。只登记这些操作通过，不扩称B独立1秒、重启、G2～G5或资源全部通过。

新增失败：自动收起中点击海报外，恢复展开；自动展开中普通点击，瞬间恢复收起。

真实 PID59180 日志 `out/manual/v3-04-m08-07/basic/logs/desktopup.jsonl` 中，两种方向均出现取消。例：请求42为展开，16:23:35（本地时间）完成结果Cancelled；请求53为收起，08:26:01.941 UTC发起，08:26:02.451进入Protected并发出cancel，空间日志reason=`automatic-invalidated`，08:26:02.458恢复完成，随后回执Cancelled。该链没有相反方向请求，表现是回滚，不是反向策略求解。

旧日志未记录具体保护位，不能凭它断言每一次都来自同一个原生API。代码和确定性夹具进一步确认：

1. `NativeDesktopPointerPlatform`将全局物理按键报告为PointerButton，将当前/前台capture或移动缩放报告为Gesture；与鼠标是否在海报上无关。
2. `PassivePosterPointerObserver`也把输入路由刚刚按下获得的capture当作Gesture，此时尚未达到输入岛5px拖动阈值。
3. `AutoPostureModel.Invalidated`将任何保护位用于取消InFlight，混淆了“禁止新请求”和“中止既有请求”。
4. `CancelAutomatic → CancelPosture → FinishPosture`正确地恢复committed布局；事务提交之前仍保存旧姿态，所以两个方向恰好呈现相反的跳回。

旧生产模型上新增4个连续用例（展开/收起×内/外点击）全部在不应存在的取消回执处失败，证据为 `out/verify/v3-04-m08-07-r1/click-before.trx`。这不是画面录像，但可独立重现同一取消机制。

## 2. 修订边界

| 输入/阶段 | 等待、倒计时、出队前 | 已交付且正在动画 |
| --- | --- | --- |
| 普通物理按键、临时指针capture/前台移动缩放 | 阻止新自动事务；释放后重判并重计完整离开延迟 | 保持同一请求，不因这一原始输入单独取消或反向播放 |
| 真实海报拖缩、明确手动姿态命令 | 手动优先，清除旧资格 | 保留原有手动取消/恢复通道；不新增最后意图队列 |
| 活动菜单、编辑草稿、确认、真实DragDrop保护 | 原有保护保持 | 仍取消；不是普通空白点击，不能让菜单/确认落点被邻居推走 |
| Unknown、隐藏/未Ready、会话/环境变更、关闭或改变策略、退出 | 不发起 | 仍取消一次，等精确恢复回执后释放单航班 |
| 按键仍按下时动画成功完成 | — | 完成原目标，但不启动下一张/反向请求；释放后按当前姿态与指针重新判断 |

原始按键不等于语义操作：点击“…”或收展按钮仍走既有功能。没有将这些按钮变为无效，也不承诺菜单打开或真正拖动时动画必须继续。

实现：新增临时`PointerCapture`保护位；Native观察和router按下捕获使用它，真正空间手势继续使用Gesture。模型只在InFlight过滤PointerButton/PointerCapture，出队前所有保护仍有效。调度在实际失效点记录一次`auto_posture.invalidated`及局部/共享保护、presence、策略/代次，不记录全局鼠标坐标或持续轨迹。

未改空间求解、碰撞、推让/条件归位、R4容量/内容租约、输入岛命中和5px阈值、单航班回执或SQLite schema/CAS。
