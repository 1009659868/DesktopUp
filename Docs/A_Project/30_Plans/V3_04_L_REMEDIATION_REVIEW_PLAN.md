## 3. 顺序的多方面考量

| 考量 | 对顺序的影响 |
| --- | --- |
| 产品目标 | 先保证内容可达、动作可预测、配置可恢复；不继续为外壳和排版无限延期Item |
| 数据安全 | 先保全dirty树与旧配置并阻止静默丢字段；迁移必须建立在明确语义之后 |
| 交互语义 | 图钉含义会影响拖动、最小尺寸、切轴、撤销、热度和迁移；它是前置决定，不能最后补文案 |
| 几何依赖 | 卡片/区域约束决定extent；extent决定有限末端和循环周期；同一主轴抽象先定，不能边修循环边改挤压定义 |
| 生产风险 | 纯模型/真实命令先证伪，再小范围接原输入/R4；尽早验证首次拖动，不把所有风险积到最终人工 |
| 演示与真实数据 | 演示使用DEMO；已存在配置保真照样要保障；真实文件执行必须等待V3-05恢复账本门 |
| 成本与回退 | 分块只改内容通道，保留旧包/配置/失败证据；不用一次“大重构”混入主题、自动收展或桌面宿主 |
| 证据可信度 | 同一源、构建、manifest、进程门、人工范围绑定；不能补改hash使旧PASS看起来有效 |

总顺序：**评审语义及UI C范围 → 保全与安全底线 → 统一几何/浏览模型 → 编辑/事务/兼容模型 → UI C核心界面与真实操作 → 被动变化与循环组合 → 同包人工 → Item主线**。

有限/循环数学规则在统一浏览模型中一起定义，但生产先接有限浏览，循环组合随后增量接入。这不是取消循环，也不是再写两个滚动器。

R1收口后，R3/R4期间以隔离数据验证UI C最小原生样板，及时暴露WinUI呈现、命中与控件绑定限制；R5交付核心界面，R7在同一最终界面验收。不等全部模型完成才接UI，也不要求先完成V3-07模板平台。样板沿用生产端口/输入/呈现机制，不成为第二套solver或持久状态。

### 4.3 配置保真、可靠性与Item接入出口

当前能力缺口（2026-09-27）：SQLite12已保存配方/中心主题，但Portable v4对自定义目录、非light主题或RecipeInstances明确拒绝。这是防静默丢字段的安全底线，**不等于下面完整配置往返出口已满足**。模块迁移后、R7验收前须补受支持新字段的版本化携带与恢复验证；若拟限制交付范围，须带具体影响由用户裁决，不在本次文档审计中自动降低验收标准。未知/损坏格式仍保持拒绝或原文备份。
