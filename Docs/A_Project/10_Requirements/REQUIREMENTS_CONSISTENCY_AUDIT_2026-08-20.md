# Desktop-Up V2 完整需求一致性审计

状态：`COMPLETED — REQUIREMENTS FROZEN / NON-NORMATIVE EVIDENCE`

审计对象：`Docs/A_Project/10_Requirements/` 下七份需求文档

## 1. 审计目的

本审计检查七份需求是否存在：

- 同一行为被重复定义且结论不同；
- P0 不变量被专项验收放宽；
- 已裁决项仍被列为待决；
- 应有需求缺失或只存在于历史讨论；
- 产品要求夹带具体框架、格式、API、存储或系统实现；
- 延期范围与当前范围互相覆盖；
- 验收次数、环境和通过条件不一致；
- 文档数量、阶段状态和阅读入口未同步。

本文件只记录审计证据，不是第八份需求权威。经修订后的七份需求文档仍是唯一需求集合。

## 2. 审计方法

1. 逐份通读完整需求画像及六份专项/支持文档；
2. 按“产品范围、P0 不变量、运行表面、Item、主题/AI、数据、安全、安装、验收、延期、待定项”建立横向矩阵；
3. 冲突时以用户最新明确决策和 P0 安全/桌面不变量为上位约束；
4. 区分产品可观察行为、平台约束和实现决定；
5. 对每个待定项建立一个全局 ID，并把专项别名映射到该 ID；
6. 修订后执行术语、链接、状态、实现词和遗留计划引用复查。

## 3. 审计结论摘要

- 共识别 13 类一致性问题；
- 其中 2 类会直接放宽 P0 行为：Win+D 通过条件和精确桌面层级缺失；
- 5 类属于实现预绑定：样式/对象模型、包格式、参数 schema、凭据后端和自启位置；
- 4 类属于状态或范围不同步：默认主题、USING 双击、自动清理/安全收纳、已裁决项仍列 TBD；
- 2 类属于治理元数据过期：待定项索引不完整、迁移文档仍写五份权威文档；
- 修订后没有发现未解决的 P0 内部矛盾；剩余问题均已登记为显式 TBD 或 DEFERRED，不允许由实现自行猜测。

## 6. 重复项处理原则

以下重复属于有意重复，不删除，但职责不同：

- P0 层级和输入同时出现在画像、视觉、运行与风险文档：画像定义不变量，专项给验收，风险文档给反例与关闭证据；
- 状态 revision/CAS 同时出现在画像、运行和主题文档：画像定义单一权威，运行定义表面同步，主题定义预览/提交防回弹；
- fallback 同时出现在视觉、主题和画像：画像定义优先级，视觉定义用户可见形态，主题定义包/切换错误处理；
- 安全收纳同时出现在画像与 Item 文档：画像定义用户文件底线，Item 文档定义发现、预览、确认和恢复语义。

专项文档不得复制一套不同默认值；全局待定状态只由统一待定表维护。

## 7. 保留的平台与产品约束

以下术语不是需要删除的实现假设：

- Windows 11 x64、当前用户安装、Windows/Shell 等价启动语义；
- 可观察的窗口层级、任务栏、Alt+Tab、Win+D、Explorer 重建和 DPI/分辨率事件；
- revision/expected-revision/CAS、事务、原子替换、last-known-good 等一致性性质；
- 安装器、主程序、自启标识和卸载恢复等发布产品契约；
- OpenAI、DeepSeek 和 OpenAI-Compatible 作为用户可选择 Provider 的产品范围。

它们约束外部行为或平台边界，但不预选 UI 框架、渲染 API、语言、进程拓扑、IPC、数据库、包容器或 Windows API。

## 8. 仍开放但不阻止需求冻结的事项

统一待定表保留 12 项。它们均满足以下条件之一：

- 需要在技术选型/架构阶段用证据决定，如呈现技术、进程边界、包格式；
- 需要后续产品标定，如衰减公式、排版阈值、视觉终稿；
- 属于明确延期，如多海报与多显示器完整认证；
- 在对应实现前有明确决策门，如启动成功统计门。

这些事项不改变当前 P0 不变量和初始单海报范围，因此可以在需求冻结后继续处理，但不得被实现默认补全。
