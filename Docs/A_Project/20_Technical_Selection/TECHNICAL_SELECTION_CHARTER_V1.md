# Desktop-Up V2 技术选型章程 V1

状态：`ACTIVE — TECHNOLOGY NEUTRAL`

日期：2026-08-20

## 1. 目的

技术选型要回答的不是“哪个 UI 框架看起来方便”，而是：哪组技术能够在 Windows 11 上长期、稳定、可诊断地实现冻结需求，尤其是透明海报、桌面输入穿透、精确层级、Win+D 连续可见、主题自由度、低资源、状态一致性和安全恢复。

选型结果可以是单一框架，也可以是按表面拆分的组合；但任何组合都必须说明边界成本，不能把无法解决的问题推给尚未定义的“原生层”或“以后再修”。

## 2. 决策范围

| 决策域 | 本阶段要确定的内容 | 不在本阶段确定的内容 |
| --- | --- | --- |
| TS-D01 海报呈现 | 绘制/布局/文字/图片/透明合成/动画的技术家族 | 最终类名、文件布局和业务组件拆分 |
| TS-D02 Windows 桌面宿主 | 窗口能力、桌面层适配、命中、非激活、z-order、Win+D 与 Explorer 恢复的可行技术 | 最终窗口状态机实现细节 |
| TS-D03 控制中心 UI | 普通窗口、预览、表单、键盘和无障碍所需 UI 技术 | 最终页面设计和组件层次 |
| TS-D04 核心运行时 | 适合承载状态、托盘、生命周期、Shell、安全收纳和诊断的语言/运行时 | 最终模块边界和线程模型 |
| TS-D05 权威存储 | 满足事务、迁移、revision/CAS、备份和损坏恢复的存储技术 | 最终表结构和迁移脚本 |
| TS-D06 进程通信 | 候选通信技术、版本化消息和故障语义 | 最终进程拓扑；若单进程则可不启用 IPC |
| TS-D07 主题表达与隔离 | 参数、素材、结构、样式、包和受限覆盖的表达/校验技术 | 最终主题 API 和市场协议 |
| TS-D08 安装与生命周期 | 当前用户安装、自启、升级、独立卸载和依赖交付技术 | 最终安装界面文案 |
| TS-D09 验证与诊断 | 自动化、窗口遥测、录屏、性能和故障注入工具 | 产品内最终诊断 UI |

TS-D01 与 TS-D02 是首要 P0 决策。它们未通过前，不得因为某个控制中心框架更易开发就倒推海报技术。

## 3. 非目标

- 不在本阶段开发生产功能或迁移旧实现；
- 不把原型代码直接晋升为正式架构；
- 不确定产品视觉终稿、活跃度公式或编辑态双击等产品 TBD；
- 不执行多显示器/混合 DPI 的完整发布认证，但候选不得从结构上封死该能力；
- 不比较与冻结需求无关的通用基准；
- 不以“生态大”“现代”“原生”“跨平台”等标签代替证据。

## 4. 选型原则

### TS-PR-01 P0 硬门优先

层级、Win+D、输入、异常边框、用户文件、状态和故障隔离是淘汰门。候选即使开发效率或视觉分更高，也不能用总分抵消 P0 失败。

### TS-PR-02 同构比较

候选必须使用相同 Night Ops 画面、相同六 Item/零 Item/失效 Item 夹具、相同几何、相同动作次数、相同设备和相同证据格式。不能用一个完整 Demo 与另一个空窗口比较。

### TS-PR-03 事实与推断分离

- 官方资料支持的内容标为 `FACT`；
- 本机可复现结果标为 `MEASURED`；
- 尚未验证的判断标为 `HYPOTHESIS`；
- 历史 V1/V2 故障标为 `HISTORICAL`，不能外推到新候选；
- 缺证据统一标为 `UNKNOWN`，不能写成 PASS。

### TS-PR-04 工作量必须闭合

如果候选需要 Windows 原生适配层，事实卡必须说明适配层负责什么、如何验证、失败如何诊断。无边界的“少量 native code”按未知高风险处理。

### TS-PR-05 无默认赢家

候选登记顺序不是优先级。历史上使用过 WebView2、Qt 或 Rust，不增加也不降低新候选分数。个人熟悉度只进入“团队学习与维护成本”评分，不改变硬门。

### TS-PR-06 版本与分发是选型组成

候选必须固定被测试的版本、工具链、运行时、许可证和分发依赖。只验证开发机能运行，不等于可安装或可维护。

### TS-PR-07 结论可推翻

所有淘汰和选择必须指向原始证据。发现测试方法错误、候选版本变化或需求变更时，可以重开对应矩阵项，但必须保留旧证据和原因。

## 5. 候选进入规则

候选进入事实审查至少需要：

- 能在 Windows 11 x64 上创建自定义桌面表面或与原生宿主组合；
- 能表达 Night Ops 级别画面、响应式 Item、文字、图片、透明和基本动画；
- 有可固定版本的工具链和可审查的分发许可；
- 能提供调试或外部诊断手段；
- 没有已知不可绕过且直接违反冻结 P0 的事实。

候选可以由用户或后续研究新增。新增候选必须接受完整矩阵，不能只比较优势项。

## 6. 淘汰与保留规则

### 6.1 直接淘汰

- 官方限制明确导致 P0 无法实现，且不存在有界、可验证的适配层；
- P0 最小原型重复两次仍失败，失败可稳定复现；
- 必须依赖注入 Explorer、常驻 TopMost、整屏输入遮罩或用户不可接受的安全越界；
- 无法在目标安装权限和分发边界内合法、稳定交付；
- 关键依赖不可固定、不可获得或缺少可接受维护路径。

### 6.2 有条件保留

候选需要一个范围明确的适配层时，可以保留一次修正机会，但必须先登记：

- 适配层 API 和所有权；
- 新增依赖与故障面；
- 预计代码量/复杂度区间；
- 新增验证项；
- 如果修正失败的退出条件。

### 6.3 进入评分

只有全部 P0 硬门为 PASS 的候选才进入加权评分。`UNKNOWN`、`PARTIAL` 和“肉眼看起来正常”均不算 PASS。

## 7. 证据等级

| 等级 | 证据 | 可支持的结论 |
| --- | --- | --- |
| E0 | 无来源判断、聊天结论、记忆 | 只能提出假设 |
| E1 | 官方文档、许可证、支持矩阵 | 支持静态可行性或限制，不证明运行行为 |
| E2 | 可复现最小原型、源码、命令和日志 | 支持单场景本机结论 |
| E3 | 同一候选重复运行、故障注入、视频与遥测一致 | 支持硬门 PASS/FAIL |
| E4 | 多环境/净机/长时复测和独立复核 | 支持最终选型与发布风险判断 |

P0 淘汰至少需要 E1 明确不可行或 E3 可复现失败。P0 通过至少需要 E3；最终选择的关键链路应在架构冻结前补到 E4。

## 8. 阶段顺序

```text
冻结需求与矩阵
→ 候选事实审查
→ 静态淘汰不可行候选
→ 同构 P0 最小原型
→ 有界修正与一次复测
→ 支撑技术域短名单
→ 完整统一矩阵
→ 加权评分与敏感性分析
→ 用户评审
→ 决策记录
→ 架构设计输入
```

## 9. 变更控制

- 冻结需求变化：所有受影响候选重新评估；
- 矩阵变化：说明原因并对全部候选补测，不能只给偏好的候选加分项；
- 权重变化：保留旧权重结果并执行敏感性分析；
- 候选版本变化：建立新事实卡和独立结果，不覆盖旧运行；
- 原型发现新风险：先登记风险，再决定是否新增硬门。

## 10. 阶段交付物

- 固定版本的候选事实卡；
- 同构最小原型与复现命令；
- 完整证据目录；
- 硬门 PASS/FAIL/UNKNOWN 汇总；
- 加权评分与权重敏感性分析；
- 选择、淘汰、残余风险和可逆性说明；
- 给架构阶段的技术约束清单。
