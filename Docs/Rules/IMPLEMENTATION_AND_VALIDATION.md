# DesktopUp 实施与验证流程

2026-10-12起执行。按用户要求减少重复验证、过细交付和重复文档维护，以完成可用功能为推进单位。历史测试继续保留，但不把累计回归库当成每次任务的必跑清单；本规则调整执行频率，不取消产品安全约束或补记未验项通过。

## 实施与交付

- 开始任务只确认用户可见结果、受影响模块和必要风险，不为每个内部方法另立合同或验收阶段。已有合同不变时直接复用；只有新增或改变行为语义才修订合同。
- 模型、持久化、接线是内部实施顺序，不是默认的三轮交付。授权范围内连续实现到可运行的功能，只在关键用户选择、权限、真实阻塞或人工验收处停下。
- 优先复用已有测试。新增用例对应新行为边界、安全不变量或已发现缺陷，不按内部类和分支机械扩张，也不规定固定用例数量。遇到重复覆盖时合并到维护中的测试；删除前核对保护范围，不集中清空历史测试。

## 按影响选择验证

| 改动 | 日常必做 | 扩大验证的时机 |
| --- | --- | --- |
| 文档、文案、静态样式 | 文档链接/差异；涉及产品时做对应构建和界面检查 | 不自动触发合同全量或全套进程矩阵 |
| 局部逻辑、新功能开发中 | 受影响项目构建；改动行为与直接依赖模块的定向测试 | 出现跨模块失败或影响面无法确定时扩大 |
| 文件移动、迁移、共享事务、原生输入归属 | 上述定向验证，加本次受影响的安全失败/取消/重启边界；文件只用隔离数据 | 修改共享基础设施、schema或全局生命周期时增加全量合同；只选相关进程场景，不搭载所有历史门 |
| 可运行功能完成、准备人工候选或里程碑交付 | 最终代码跑一次全量合同；按改动跑必要集成/原生检查，集中构建候选 | 不复跑未受影响的历史人工项目；发布另按发布规则执行 |

调试失败先重跑失败项及相邻覆盖；候选最终全量失败则修复后再完成全量，不凭局部通过宣布整体通过。未改源码时复用同一构建，源码改动后不得用旧程序集冒充新验证。全量命令 `scripts/test.ps1`保留；开发中的定向运行使用`dotnet test --filter`，记录实际过滤范围。

数据安全不得省略：不覆盖用户目标、不误删唯一完整副本、提交失败可安全收尾、共享引用保持一致、取消/重复回调不重复提交。只验证本次改动涉及的边界，复用其已有覆盖，不因追求速度绕过文件所有权或账本检查。

## 测试数据与收尾（2026-10-16）

- 自建样例默认放在本批隔离目录，建立创建/转移的精确路径与身份或哈希清单；不得用用户真实文件充当可自动清理样例。
- 确需验证真实桌面兜底等外部落点时，事先明确落点和收尾范围。测试结束或用户确认本批通过后，核对清单及实际结果，清理本批生成且仍能确认归属的样例；不得把收尾留给用户或把样例混入正式首启数据。
- 收尾仅使用明确允许的单文件/目录路径，不按桌面前缀通配删除，不递归清空桌面、收纳库或配置。身份/内容变化或来源不明的对象保持原位并报告；真实文件、用户配置、映射目录及原始证据不动。
- 优先可恢复清理：副本核验成功后再移除外部样例，副本及清理清单放在本批隔离输出中且不入Git。结束时核对外部样例已清除、受保护文件未变，并在交付中说明；未完成的收尾如实列明。

## 候选与记录

- 日常保留测试命令、结果及必要失败日志即可，不每个小步骤构建多套候选、启动完整进程矩阵或生成全源码指纹包。
- 人工候选记录可识别的构建、产物、配置目录及对应验证范围，避免混用新旧代码结论；只有实际需要证明一致性的地方才做指纹绑定。旧proof及旧配置不篡改，产品文件完整性校验不受此简化影响。
- 当前任务文档保存详细进度和验证，交接只写结果、未完成项与下一步。入口/总计划在阶段或执行规则变化时更新，代码锚点仅在入口改变时更新；不将同一段证据复制到多份目录文档。验证日志链接任务记录即可。
- 不以新增测试数量衡量进度。交付说明优先回答“现在能做什么、还不能做什么、验证了什么”；内部子批编号保留追踪，不要求用户逐批确认。
