# A/B/C 文档治理规则

## 1. 权威规则

1. 每个层级只有一个活跃计划和一个当前交接。
2. Catalog 只能指向权威文档，不能自己成为第二份计划。
3. Plan 记录未完成工作，Log 记录已完成事实，Sync 记录当前接手状态。
4. 状态冲突时，以 `00_Catalog/ACTIVE_PATH.md` 指向的链为准。
5. 稳定技术原理不能只存在于日志；形成后应迁移到独立技术说明。
6. 设计文档中的“推荐”不自动等于已接受决策；只有状态为 `ACTIVE` 或日志记录了接受结果才具有执行权威。

## 2. 更新触发器

| 事件 | C | B | A |
| --- | --- | --- | --- |
| 完成一个实现项 | 必须更新 | 通常不更新 | 不更新 |
| 完成 C 工作流 | 必须更新 | 必须更新 | 视阶段门而定 |
| 修改跨模块契约 | 必须更新 | 必须更新 | 影响产品能力时更新 |
| 完成性能/兼容性验收 | 记录完整证据 | 记录模块结论 | 只记录阶段结论 |
| 产品优先级或范围变化 | 同步受影响任务 | 同步模块顺序 | 必须更新 |
| 交接开发环境 | 必须更新 | 活跃 B 必须可导航 | A 入口必须有效 |

## 3. 计划规则

- 任务写成可验证的结果，不按文件数量拆分。
- 每项任务必须包含依赖、完成信号和验证面。
- 当前活跃 C 之外，必须为路线中紧随其后的至少两个 C 工作流建立提前计划包；提前计划至少包含范围、非目标、依赖、预定任务、完成门、冷启动和预备交接，但不得把预备代码锚点表述为已经实现。
- C 激活时先执行现状/证据审计，再补充或缩减实施切片；已被既有工作流覆盖的结果登记为吸收证据，不为保持任务数量重复开发。
- 非公开 Windows 行为、兼容性技巧和过渡实现必须标明风险与回退路径。
- 未完成任务不得通过文档整理被删除；只能调整顺序、拆分或明确取消原因。
- 性能目标是测试预算，不是未经测量的产品承诺。

## 4. 日志规则

- C 日志按日期归档，例如 `20_Log/2026-08/2026-08-02_desktop_host_spike.md`。
- 日志至少包含目标、实现/检查、决策、验证、遗留问题和相关路径。
- 历史结论不原地改写；发现错误时新增纠正日志并相互链接。
- 纯命令输出不能单独作为证据，必须解释它证明或否定了什么。

## 5. 同步规则

- `CURRENT_HANDOFF.md` 只保留当前事实、下一步、阻塞和工作区注意事项。
- `COLD_START.md` 只规定阅读顺序和接手检查。
- 上层交接只指向必要下层，不复制下层全文。
- 交接必须区分：已计划、已实现、已验证和未验证。
