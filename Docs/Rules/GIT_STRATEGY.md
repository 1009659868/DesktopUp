# DesktopUp V3 开发与发布源码分支

2026-10-10，按用户明确要求建立双分支流程。本规则适用于 DesktopUp_V2；旧 DesktopUp 仓库的 V1／Tauri 分支规则不替代这里的实际 .NET／WinUI 项目状态。

## 分支职责

- `impl/poster-redesign-V3`：当前开发线，保留需求、设计、计划、测试、验证脚本与交接。
- `impl/main`：发布相关的精简源码线。保留产品源码、内置模块、运行配置、构建／启动／打包入口、依赖声明及许可证；不保留设计文档、测试工程、夹具、验收入口、测试探针或临时产物。
- `main`、其他分支：本次不修改。`impl/main` 不是已经完成全部人工与稳定性验收的正式发布标签。

本地候选、配置、故障日志和 `.workbuddy` 不上传、不清空。发布精简只作用于分支跟踪文件；被移除文件仍可从开发分支和 Git 历史恢复。文件校验、收纳账本、恢复安全保护、运行诊断和必要合法归属信息属于产品，不以“校验文件”为名删除。

## 里程碑同步流程

1. 在开发线完成实现、对应测试和文档，核清人工结论及携带项。提交并推送开发线，记录源提交。
   若用户要求发布验证先于远端同步（如2026-10-13），先做本地开发检查点与发布合并/验证，两线均通过后再推送；本地提交或编译成功不等于远端发布完成。
2. 确认跟踪文件干净，记录起始分支，fetch 后检查双方差异；不得强推或覆盖他人的修改。
3. 切到 `impl/main`，使用 `git merge --no-ff --no-commit <已确认的开发提交>` 保留来源。修改／删除冲突逐项审查：产品修改正常合入，发布分支退役的测试／文档继续移除，不能全局采用 ours 或 theirs。
4. 在合并提交之前重新核对发布边界。尤其检查新增加的测试／探针／验收脚本、App 启动分发、解决方案与依赖声明、打包源清单；普通 merge 不会自动过滤开发文件。
5. 独立输出目录执行 Release 构建与打包验证，确认不依赖已删目录、不携带用户数据、测试载荷或调试符号。发布分支变更后的原生人工结果不得从旧包自动继承。
6. 提交合并并推送 `impl/main`；回到起始开发分支，在交接登记源提交、发布提交、验证和携带项。不要将发布精简反向合入开发线，否则会删除开发资料。

用户已要求后续在里程碑完成时按此流程同步，不按每个小修改同步，也不把未验状态写成 PASS。遇到来源不明修改、冲突无法安全判断或远端非快进时停止相关写操作并说明。
