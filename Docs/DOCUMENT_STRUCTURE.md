# Desktop-Up V2 文档结构与阅读规则

本仓库沿用 A/B/C 三层计划模型，但 V2 文档必须独立表达需求；不得用“同 V1”“沿用旧实现”代替具体说明。

## 1. 结构目标

| 层级 | 正式名称 | 回答的问题 | 更新粒度 |
| --- | --- | --- | --- |
| A | Project Mainline | 产品是什么、当前处于什么阶段、为何优先此阶段、全局完成条件是什么 | 产品范围、阶段或发布目标变化 |
| B | Capability Module | 一项能力的边界、依赖、所有权、模块里程碑和公共契约是什么 | 能力里程碑、接口或所有权变化 |
| C | Workstream | 当前具体做什么、如何验证、证据和下一步是什么 | 每个实现或验收任务 |

## 2. 每层固定分区

| 分区 | 保存内容 | 不保存内容 |
| --- | --- | --- |
| `00_Catalog/` | 下一层索引、任务索引、决策索引 | 设计正文、过程叙述 |
| `10_Plan/` | 需求、设计合同、未来工作、依赖、验收标准 | 冗长命令输出、已完成过程 |
| `20_Log/` | 已完成事实、决策结果、验证证据 | 持续变化的下一步 |
| `30_Sync/` | 当前状态、阻塞、下一动作、接手入口 | 长期技术说明和历史大全 |

## 3. 标准阅读路径

新开发者或新 Agent：

1. 根 `README.md`；
2. `Docs/README.md`；
3. `00_Catalog/ACTIVE_PATH.md`；
4. `A_Project/30_Sync/COLD_START.md`；
5. 当前活跃 A/B/C 的计划、任务索引和交接。

当前尚未激活 B/C，因此必须先完整阅读 A 层需求和四份领域设计合同。

## 4. 权威与历史证据

- `A_Project/10_Plan/` 下标记为 `ACTIVE` 的 V2 文档是当前产品与设计权威；
- `Reference/V1_Design_Source/` 是迁移时的只读历史快照，只用于追溯来源和查漏；
- 历史证据与 V2 当前文档冲突时，以用户最新决策和 V2 活跃文档为准，并在迁移追踪表登记差异；
- 不删除仍能解释历史决策的材料，但必须明确其状态，避免旧任务重新成为当前计划。

## 5. 同步触发器

- C：任务完成、阻塞改变、验证完成或结论被推翻时更新；
- B：模块里程碑、接口边界、依赖或主要工作流改变时更新；
- A：产品范围、阶段、优先级、发布目标或关键技术方向改变时更新；
- `20_Log` 保存历史事实，原则上不回写；若旧结论被取代，应新增说明而不是抹去历史；
- 权威需求变更时必须同步迁移追踪表、当前交接和问题台账。

## 6. 状态枚举

`DRAFT / PROPOSED / ACTIVE / BLOCKED / COMPLETE / SUPERSEDED / HISTORICAL`

## 7. 当前阶段特别规则

- 当前只迁移文档；技术选型、代码重构和实现测试均未启动；
- 任何候选技术名称只能作为未来比较对象出现，不能写成默认首选；
- 不把旧代码、旧测试、构建产物或二进制复制进 V2；
- V1 设计原文允许复制进 `Reference/`，但必须保持只读历史身份。
